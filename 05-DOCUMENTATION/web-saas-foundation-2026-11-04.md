# گزارش فاز نخست وب چندفروشگاهی MAJORA — ۴ نوامبر ۲۰۲۶

## تصمیم فنی

پروژهٔ موجود Android/Capacitor حفظ شده است. وب تازه در `01-CORE-PLATFORM/apps/web` و API در `01-CORE-PLATFORM/apps/web-api` به همان مونوریپو افزوده شد. SQLite گوشی منبع دادهٔ وب نیست. کاربران وب روی دیتابیس مرکزی SQL Server کار می‌کنند و هر رکورد عملیاتی `TenantId` دارد. SQLite سرور فقط برای توسعه و آزمون محلی است.

ابزار طراحی UI UX Pro Max Complete برای سلسله‌مراتب، تراکم، RTL، واکنش‌گرایی، حداقل سطح لمس، کنتراست و کاهش حرکت استفاده شد. رنگ‌های اجرایی و Estedad از سیستم طراحی مشتری اول آمده‌اند. Idea Storm X به تصمیم «مدیر هوشمند باید دادهٔ قابل اتکا و اقدام قابل پیگیری داشته باشد؛ پاسخ آزاد بدون داده ارزش ندارد» منجر شد؛ اکنون فقط خلاصهٔ داده و پرسش متنی محدود پیاده شده است.

## شواهد اجرا

- SDK رسمی .NET 10.0.403 نصب شد؛ API با EF Core 10.0.14 و SQL Server/SQLite بدون هشدار کامپایل شد.
- وب React/TypeScript با Vite ساخته شد. خروجی استاتیک در `apps/web-api/wwwroot` برای انتشار API قرار می‌گیرد.
- مهاجرت‌های SQL Server در `apps/web-api/Migrations` ساخته شدند و اسکریپت idempotent انتشار تولید شد؛ اجرای آنها روی SQL Server واقعی هنوز آزمون نشده است. Production تا اعمال migration باز نمی‌شود.
- آزمون HTTP در `tooling/test-web-api.ps1`: ورود، طرح/اشتراک، ساخت دو فروشگاه، ثبت کالا/مشتری، صدور فاکتور، idempotency، کسر موجودی، دریافت تکمیلی، خرید، هزینه، بهای تمام‌شده، نقش کارمند، CSRF، تعلیق و منع دسترسی فروشگاه دوم به دادهٔ اول **قبول** شد.
- صفحهٔ ورود در مرورگر دسکتاپ و عرض ۳۹۰ پیکسل موبایل بازبینی شد. این بازبینی، آزمون کامل تمام صفحه‌ها یا دستگاه‌های واقعی نیست.
- دارایی‌های اصلی در `00-COMPANY/brand-assets` و `02-CLIENT-PROJECTS/.../original-assets` تغییر نکردند. نسخه‌ای از نشان ماژورا و فونت برای وب کپی شد.

## مواردی که هنوز برای «نسخهٔ کامل قابل فروش» لازم‌اند

1. انتقال امن داده‌های SQLite اپ Android به هر فروشگاه وب و تطبیق شناسه‌ها/فاکتورهای قدیمی؛ هیچ دادهٔ گوشی در این فاز وارد نشده است.
2. انتقال کامل قالب فاکتور تصویری تأییدشده، صفحه‌بندی A4/A5، PNG و PDF سروری، فونت و شروط نسخه‌دار، و آزمون چاپ واقعی. پیش‌نمایش فعلی قالب ساده است.
3. حسابداری دوطرفه با سرفصل، چک، مرجوعی، انبار چندمرحله‌ای، تراز و گزارش سود معتبر؛ بخش فعلی خرید/هزینه/بهای میانگین و برآورد عملیاتی است و «حسابداری کامل» نیست.
4. تنظیمات کامل برند در پنل، عکس کالا و ضمیمه، بایگانی/حذف، قیمت گروهی، جست‌وجوی سراسری، گزارش‌های پیشرفته و خروجی Excel/CSV.
5. اتصال پیامک ایرانی، صف ارسال و webhook تحویل؛ اعلان Web Push/موبایل؛ اکنون فقط یادآور در خود وب دیده می‌شود.
6. درگاه پرداخت اشتراک، صدور صورتحساب MAJORA و تمدید خودکار؛ اکنون مدیر اشتراک را دستی ثبت می‌کند.
7. AI عملیاتی با مجوز دسترسی ریز، گزارش منابع، ارزیابی پاسخ، محدودیت هزینه و تأیید انسانی قبل از هر تغییر مالی؛ endpoint خارجی بدون تنظیمات فقط پاسخ قاعده‌ای می‌دهد.
8. آزمون SQL Server واقعی، فشار هم‌زمان، امنیت، مرورگرهای اصلی، بازیابی پشتیبان، عدم دسترسی شبکه و آزمون کاربران واقعی.

تا پایان این موارد، این خروجی «زیرساخت و نمونهٔ اجرایی وب» است و نسخهٔ نهایی بی‌نقص یا آمادهٔ استقرار با دادهٔ واقعی مشتری نامیده نمی‌شود.

## ملاحظات طراحی داده و امنیت

- همهٔ قیمت‌ها و موجودی‌ها عدد صحیح `long` هستند. فاکتور صادرشده snapshot کالا و قیمت دارد؛ تغییر قیمت کالا فاکتور گذشته را تغییر نمی‌دهد.
- فرم‌های React فعلاً مبالغ را با نوع `number` جاوااسکریپت نگه می‌دارند؛ برای مبالغ خارج از بازهٔ صحیح امن جاوااسکریپت، نمایش و محاسبه تضمین نشده است. پیش از پذیرش مبالغ بسیار بزرگ باید ورودی/خروجی پول به رشتهٔ ده‌دهی تبدیل شود.
- هر درخواست کسب‌وکار با `TenantId` کوکی احراز هویت فیلتر می‌شود. کنترل فعال بودن کاربر و فروشگاه در هر درخواست انجام می‌شود. تغییر رمز نسخهٔ نشست را بالا می‌برد و کوکی‌های پیشین را بی‌اعتبار می‌کند.
- عملیات صدور فاکتور و دریافت تکمیلی داخل تراکنش Serializable و همراه audit ثبت می‌شود. شناسهٔ idempotency مانع صدور دوبارهٔ همان درخواست می‌شود.
- مدیر MAJORA فقط دادهٔ مدیریتی فروشگاه/اشتراک را در UI دارد؛ دسترسی پشتیبانی به دادهٔ مالی هر فروشگاه باید در آینده با رضایت مالک، زمان‌دار و قابل حسابرسی طراحی شود.
- پاسخ مشاور از آمار تجمیعی ۳۰ روز ساخته می‌شود و نام/تلفن مشتری به سرویس AI فرستاده نمی‌شود. کلید AI فقط در محیط سرور می‌ماند.
