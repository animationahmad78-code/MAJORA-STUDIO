# گزارش تکمیل اصلاح نسخه‌دار فاکتور وب — ۹ نوامبر ۲۰۲۶ UTC

این تغییر روی همان شاخهٔ `feature/web-invoice-parity` در مونوریپوی MAJORA-STUDIO انجام شد. **این نسخه هنوز محصول نهایی قابل فروش یا معادل کامل APK نیست.** دادهٔ آزمون در پایگاه جداگانهٔ محلی ساخته شد.

## تغییر اجراشده

- نسخهٔ ۱ فاکتورهای تازه در لحظهٔ صدور به‌صورت snapshot مستقل ذخیره می‌شود؛ پرداخت‌ها و تغییرات بعدی آن را بازنویسی نمی‌کنند. برای سندهای قدیمیِ پیش از این مهاجرت، نخستین اصلاح نسخهٔ موجود در آن لحظه را به عنوان مبنا ثبت می‌کند؛ بازسازی لحظهٔ صدور از دادهٔ موجود ممکن نیست.
- فرم «ویرایش فاکتور» در فهرست وب، اصلاح نام/تلفن مشتری، تاریخ شمسی، شرح/تعداد/فی/تخفیف ریالی ردیف‌ها و افزودن قلم دستی را ارائه می‌کند. شمارهٔ فاکتور ثابت می‌ماند؛ نسخهٔ جدید و دلیل اصلاح در سابقه باقی می‌مانند.
- در تراکنش واحد، اختلاف تعداد اقلامِ کاتالوگی با موجودی تطبیق داده و حرکت انبار ثبت می‌شود. اصلاح با نسخهٔ قدیمی، موجودی ناکافی، مبلغ کمتر از وجه دریافت‌شده یا مرجوعی قبلی رد می‌شود. تغییر هویت مشتری، پیوند سوابق او را به مشتری سازگار منتقل می‌کند.
- API سابقهٔ نسخه‌ها فقط برای همان فروشگاه قابل خواندن است. مهاجرت SQL Server برای جدول نسخه‌ها و ستون `Revision` ساخته شد؛ دیتابیس توسعهٔ SQLite جدول‌ها را از مدل جدید می‌سازد.
- تبدیل پیش‌فاکتور به فروش نیز نسخهٔ تازه ثبت می‌کند تا متن پیش‌فاکتور قبلی و وضعیت فروش پس از تبدیل قابل تشخیص بمانند.

## محدودیت‌های باقی‌مانده

- فرم اصلاح فعلاً کالای جدید کاتالوگ را با جست‌وجو به فاکتور نمی‌افزاید؛ قلم دستی را می‌افزاید. بعد از مرجوعی، اصلاح مستقیم بسته است و جریان سند تعدیلی مستقل لازم است. امکان دیدن/چاپ snapshot نسخه‌های پیشین در رابط هنوز نیست.
- اصلاح فاکتور هنوز همهٔ فیلدهای قالب Android را ندارد. خروجی چندصفحه‌ای و چاپ فیزیکی، SQL Server واقعی، چند دستگاه، پیامک، چک/دفترکل، پشتیبان سرور و مشاور AI واقعی آزمون یا تکمیل نشده‌اند.
- بستهٔ وب فعلاً برای محیط آزمایشی و بازبینی است. استقرار تجاری باید پس از آزمون مهاجرت SQL Server، پشتیبان و بازیابی، امنیت، دستگاه و کارکرد واقعی انجام شود.
