# گزارش ادامهٔ ساخت MAJORA — ثبت فروشگاه و پیش‌نمایش چک

وضعیت این گزارش: کد و آزمون‌های محلی انجام شده‌اند؛ آزمون مرورگری واقعی، SQL Server و پذیرش مشتری هنوز باز است. این بسته «نهایی قابل فروش» نام‌گذاری نمی‌شود.

## تغییرات

- پنل مالک، ساخت فروشگاه را در پنج مرحلهٔ هویت، برند و فاکتور، اشتراک، حساب مالک و بازبینی انجام می‌دهد. اطلاعات فرم در بازگشت بین مراحل و پس از خطای ثبت حفظ می‌شود.
- API همان درخواست ساخت را با قالب اختصاصی، مالک و اشتراک در یک `SaveChanges` ثبت می‌کند. شناسه و نام کاربری تکراری با پاسخ کنترل‌شده رد می‌شوند و ارسال دوبارهٔ همان درخواست، فروشگاه جدید نمی‌سازد.
- قالب آمادهٔ کیف و کمربند کلاسیک، شامل لوگو و مشخصات واقعی آن فروشگاه، برای هر نام دیگری در سرور رد می‌شود. فرم نیز این انتخاب را برای فروشگاه دیگر غیرفعال می‌کند.
- اشتراک در انتظار تأیید از پنل مالک، پس از بررسی واقعی پرداخت، با دلیل ثبت‌شده به پرداخت‌شده تبدیل می‌شود. درخواست تکراری همان تأیید، اشتراک دوم نمی‌سازد.
- ثبت دستی اشتراک با بازهٔ هم‌پوشان، حتی با وضعیت پرداخت متفاوت، رد می‌شود تا دو دورهٔ متعارض برای یک فروشگاه ساخته نشود.
- عکس چکِ انتخاب‌شده برای نمایش در فاکتور از مسیر مختص همان فاکتور و همان فروشگاه دریافت می‌شود؛ صندوق‌دار برای پیش‌نمایش به دسترسی حسابداری نیاز ندارد.

## شواهد و محدودیت

- ساخت React و .NET بدون خطای کامپایل گذشت.
- ۴۰ آزمون واحد گذشت.
- سناریوی API با ساخت ۲۰ فروشگاه، ثبت تکراری، شکست ثبت نامعتبر بدون رکورد نیمه‌کاره، تأیید اشتراک، نقش صندوق‌دار و جداسازی عکس چک دو فروشگاه گذشت.
- آزمون UI در مرورگر با نقش‌های واقعی و پیش‌نمایش A4/A5 برای Wizard انجام نشده است. پایگاه SQL Server تولیدی و مسیر پرداخت درگاه واقعی نیز آزموده نشده‌اند.

۲. مدل کامل وضعیت اشتراک و جلوگیری از فعال‌سازی تکراری/هم‌پوشانی زمانی در SQL Server.

۳. آزمون استقرار، پشتیبان و بازیابی روی سرور واقعی .NET/SQL Server همراه با حساب و سرویس‌های بیرونی.
