# اجرای بریف پایدارسازی MAJORA SaaS — ۹ نوامبر ۲۰۲۶

این گزارش فقط وضعیت **سورس جاری** را بیان می‌کند. سرور مشتری، SQL Server عملیاتی، کلید واقعی GPT/Gemini و مرورگر چنددستگاهی در این فاز آزمون نشده‌اند. این نسخه هنوز مجوز برچسب «نهایی و قابل فروش» ندارد.

## اصلاحات انجام‌شده

| شناسه | نتیجه و شاهد |
|---|---|
| BRAND-01 | `PUT /api/merchant/invoice-brand` در سرور `403` برمی‌گرداند. نمایش تنظیمات هویت برای فروشگاه فقط خواندنی است. مدیر از مسیر اختصاصی با دلیل و شمارهٔ نسخه قالب را تغییر می‌دهد؛ تغییر نام و هش لوگوی قدیم/جدید در ممیزی ثبت می‌شود. تصویر هویتِ فاکتور صادرشده در snapshot آن ثابت می‌ماند. آزمون HTTP هر سه مسیر را پوشش می‌دهد. |
| SUB-01 | مسیر واقعی `POST /api/admin/tenants/{id}/subscription` با فرانت یکسان شد و در آزمون HTTP موفق است. ارسال مجدد همان اشتراک همان شناسه را می‌دهد و تعارض، `409` می‌دهد. وقوع `404` در سرور مستقر پیشین هنوز از راه دور بررسی نشده است. |
| SUB-02/SUB-03 | غیرفعال‌سازی و فعال‌سازی دوباره، مشاهدهٔ همان اشتراک از پنل فروشگاه و تغییر شمار فروشگاه‌های واقعاً فعال در پنل مدیر در آزمون HTTP موفق بود. وضعیت فعلی هنوز مدل سه‌گانهٔ اشتراک/پرداخت/دسترسیِ بریف را ندارد. |
| AUTH-01 | مدیر و فروشگاه کوکی و CSRF جدا دارند؛ در یک نشست مرورگر، ورود هر دو نقش، دسترسی هم‌زمان و خروج مستقل در آزمون HTTP تأیید شد. UI تب، نقش فعال خود را در `sessionStorage` نگه می‌دارد. مرورگر واقعی پس از این تغییر دوباره آزمون نشده است. |
| AUTH-03 | بازنشانی رمز، نسخهٔ احراز هویت را تغییر می‌دهد؛ نشست قدیمی `401` می‌شود و رمز تازه وارد می‌شود. رمز فعلی نمایش داده نمی‌شود. فهرست نشست‌ها و خروج انتخابی دستگاه هنوز موجود نیست. |
| INV-01 | پس از صدور، شناسهٔ فاکتور تازه به نمای جزئیات فرستاده می‌شود. API صدور و خواندن فوری در آزمون HTTP کار کرد؛ همهٔ نماهای مرورگر دوباره بازبینی نشده‌اند. |
| AI-01 | برای Gemini Native و مسیر سازگار با OpenAI و نیز سرویس‌های سازگار با OpenAI، قالب درخواست جدا و خطاهای 400/401/403/404/429/5xx، شبکه، TLS، timeout و پاسخ نامعتبر از هم جدا شدند. پنل مدیر دکمهٔ آزمون اتصال دارد. پاسخ قاعده‌ای محلی هنگام اختلال سرویس بیرونی باقی می‌ماند. اتصال واقعی با کلید معتبر آزمون نشده است. |
| API-401/UX-01 | پاسخ‌های بدون بدنهٔ `401/403/404` اکنون پیام فارسی، کد خطا و شناسهٔ پیگیری دارند؛ شناسه در سربرگ همهٔ پاسخ‌های API نیز می‌آید. `404` با شناسهٔ متناظر در آزمون HTTP تأیید شد. خطاهای محیط مستقر هنوز ریشه‌یابی نشده‌اند. |
| ROUTE-01 | آدرس نماها در hash مرورگر ثبت می‌شود و ورود به نمای تازه اسکرول را به ابتدا برمی‌گرداند. آزمون اولیهٔ مرورگر قبل از جداسازی نشست انجام شده است. |

در آزمون یکپارچه، **۲۰ فروشگاه پیاپی** ساخته شدند و تعارض شناسهٔ تکراری رد شد. ساخت مجدد همان فروشگاه، همان شناسه را برگرداند. فرم فروشگاه با نام مالک خالی و فرم اشتراک با تاریخ وارونه ابتدا خطای `400` دادند؛ سپس بدون خروج از نشست ثبت معتبر موفق شد. این آزمون رفتار API را تأیید می‌کند و جای آزمون بازیابی همهٔ فرم‌های مرورگر را نمی‌گیرد. دادهٔ آزمون در SQLite موقت بود و به دادهٔ واقعی مشتری دست نزد.

## موارد باز و مانع انتشار

1. **مدل وضعیت و فرایند ساخت:** Wizard شش مرحله‌ای، وضعیت‌های مستقل اشتراک/پرداخت/دسترسی، تأیید پرداخت، تمدید و گذارهای کنترل‌شده هنوز پیاده نشده‌اند. ساخت فروشگاه و اشتراک دو عملیات جدا هستند و کل فرایند یک تراکنش اتمیک نیست.
2. **امنیت و جداسازی:** بررسی تمام endpointها و فایل‌ها برای جداسازی فروشگاه، ذخیرهٔ لوگو در فضای اختصاصی هر فروشگاه، نقش‌های کامل، سقف دستگاه، نشست سروری و خروج اجباری، و آزمون نفوذ لازم است. آزمون دو فروشگاه فقط تعدادی از مسیرها را پوشش می‌دهد.
3. **خطا و قرارداد API:** پاسخ استاندارد `errorCode/message/correlationId` برای همهٔ خطاها، OpenAPI/client تولیدشده، خطایابی 401/404 محیط مستقر، و آزمون بازیابی همهٔ فرم‌ها پس از خطا کامل نیست. برای خطاهای بدون بدنهٔ 401/403/404 شناسه و پیام اضافه شده و بازیابی خودکار CSRF در فرانت انجام می‌شود؛ نمایش خطا در تمام فرم‌ها هنوز انجام نشده است.
4. **داده و UI:** همسانی تمام گزارش‌های داشبورد، مشتری، حسابداری و فاکتور با دیتابیس عملیاتی؛ شمارهٔ ردیف در همهٔ خروجی‌های A4/A5/PDF/PNG؛ قالب پول با حفظ نشانگر تایپ در تمام فرم‌ها؛ و بازبینی موبایل/دسکتاپ هنوز به آزمون پذیرش کامل نیاز دارند.
5. **هوش مصنوعی:** کلیدهای واقعی، نرخ و هزینهٔ هر فروشگاه، retry/circuit breaker/fallback به provider دوم، و آزمون خطاهای زنده هنوز فراهم نشده‌اند. محاسبهٔ مالی قطعی نباید به AI وابسته شود.
6. **عملیات تولید:** SQL Server واقعی و migration، پشتیبان و بازیابی آزمایشی، health check وابستگی‌ها، صف کار، هشدار، لاگ بدون اطلاعات حساس، تست فشار، نصب روی هاست ایران و انتشار آزمایشی انجام نشده‌اند.

## شواهد محلی این تغییر

- `dotnet build` در خروجی موقت: موفق، صفر هشدار و صفر خطا.
- `tooling/test-web-api.ps1` با SQLite موقت: موفق؛ ۲۰ فروشگاه، اشتراک و تکرار آن، قفل برند، ثبات snapshot فاکتور، نشست‌های جدا، بازنشانی رمز، بازفعال‌سازی، جداسازی دادهٔ تعدادی از عملیات مالی.
- `npm test`: ۶ فایل و ۳۴ آزمون موفق.
- `npm run build -w @majora/web`: موفق؛ هشدار اندازهٔ بستهٔ جاوااسکریپت اصلی باقی است.
- آزمون مستقیم GPT/Gemini با کلید معتبر، SQL Server، بازگردانی پشتیبان و دستگاه واقعی: **انجام نشده**.

## نصب محلی ویندوز در همین فاز

فایل‌های برنامه در `%LOCALAPPDATA%\MAJORA\LocalWeb\app` با خروجی جدید جایگزین و سرویس محلی دوباره روشن شد. فایل دیتابیس ماندگار در `%LOCALAPPDATA%\MAJORA\LocalWeb\majora-local.db` جابه‌جا نشد. پیش از جایگزینی‌ها، دو پشتیبان سازگار با SQLite در `07-BACKUPS/MAJORA-local-pre-saas-20261109.db` و `07-BACKUPS/MAJORA-local-pre-saas-r2-20261109.db` گرفته شد و `PRAGMA integrity_check = ok` بود. بعد از نصب نهایی، API سلامت `ok` و صفحهٔ وب پاسخ `200` داد؛ هش فایل DLL نصب‌شده با خروجی انتشار برابر بود. دیتابیس بعد از راه‌اندازی نیز `integrity_check = ok` داشت. ورود با حساب واقعی و جریان‌های UI پس از این نصب آزمون نشده‌اند؛ این کار صرفاً دسترسی محلی به نسخهٔ جاری را فراهم می‌کند.

معیار ادامه: رفع همهٔ موانع بالا و اجرای فهرست آزمون پذیرش کاربر روی محیط نزدیک به تولید، سپس انتشار آزمایشی و ثبت نتیجهٔ بازیابی داده. این گزارش تأیید انتشار یا تضمین بی‌نقص بودن نیست.
